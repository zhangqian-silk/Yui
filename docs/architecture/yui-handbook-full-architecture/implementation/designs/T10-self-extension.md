# T10 技术方案｜原 Task 中的 Agent 自扩展

硬依赖：T03、T04、T09。

任务定义：[交付范围与证据](../tasks/T10-self-extension.md)。

## 1. 原任务闭环

自扩展是 Leader 完成原工作的一种方法，不是框架自动选择的流程。Leader发现 capability unavailable 后，判断已有工具、脚本或声明式组合是否足够，必要时再编写插件。

本任务交付必须包含一个真实原 Task 的结果：仅注册一个 hello 插件不算完成。

## 2. 稳定元工具

Session 启动时就提供 Yui CLI 或 describe／call 桥，以及 plugin.create／validate／activate。这个入口由可信内建提供，不能要求 Agent 先安装它才能安装第一个插件。

目录变化后，后续桥调用读取当前可见能力。原生工具 schema、系统提示和 Endpoint 不要求被热改。即使模型只在下一 Turn 得知新工具，也可以继续同一 Task，不重启整个 Controller。

## 3. 首个实现场景

使用授权的本地资料，任务需要把一份特殊 JSON 格式转换为报告。当前目录没有该转换能力。Leader 查询目录，选择实现小型解析／转换工具，写输入输出和测试，验证后在 Task scope 激活。

Leader 随后真实调用新能力，保存报告内容，形成 Candidate 或 direct 完成说明。测试中可放入一个格式边界，使 Leader 在验证失败后修复代码并继续，而不是由测试脚本替 Agent写最终实现。

声明式场景和可执行场景分别记录。可执行版本必须有 T09 对应运行信任证据，不以声明式成功替代。

## 4. Agent 行为指导

Role Skill 只规定复用优先、必要事实持久化、权限不足提出具体请求和不要修改核心安装目录。不规定每一步必须调用哪个工具、失败几次换模型等策略。

高智能 Leader 可以选择临时脚本完成一次性工作；不要为了统计自扩展次数强制把所有脚本注册。只有选择了插件路径时才验收注册与重复调用能力。

## 5. 权限与 scope

Task 已有授权足够时，验证和 Task-local 激活不再重复要求同样的人工批准。需要新的资源、网络、全局替换或信任级别时，由 Operator／用户处理。

Leader 不能通过新增插件覆盖核心管理能力，不能替换当前承载自己且尚未安全结束的 Endpoint。确有全局变更需要时发普通 Message 给 Operator，不创建特殊恢复工作流。

## 6. 失败与结果

语法错误、缺依赖、validation failure 作为事实返回，Leader 自己修复。插件部分完成外部动作时，Context 提供已有回执，不能修复后自动重跑整个动作链。

插件成功调用之后保存业务成果，不把 Plugin source 当成所有任务的唯一交付物。代码可以保留以便复用，历史结果读取不依赖它继续活跃。

## 7. Draft 与依赖

Active Task 首个闭环依赖 T03、T04、T09。Draft 的同类探索在 T08 可用后附加验证，不阻塞本 Task。验证时记录是否在同一 native Session、同一 Task 中继续，不能把新开完全独立任务的成功冒称原任务自扩展。

## 8. 验收

S32 证明原 Task 真实使用新能力；S33 证明验证失败能由 Leader 修复；S42 证明同 Session 通过稳定桥发现新工具；S28／S45 证明插件不扩权。

完成证据包括 Agent 实际操作记录、验证报告、激活来源、工具调用回执和业务产物。自扩展是否有价值以结果为准，不以框架新增多少对象为准。

# T00 技术方案｜实施基线与模块契约

硬依赖：无。

任务定义：[交付范围与证据](../tasks/T00-implementation-baseline.md)。

## 1. 技术目标

把目标架构落实到当前代码的责任地图，并给后续实现提供可复用的验证入口。此任务不修改用户使用路径，重点是确认“哪些代码可以替换，哪些记录不能出现第二份”。

## 2. 调研方法

先用[总体架构](../../architecture/01-overview.md)的工作关系图定位用户与 Agent，再用四个 Plane 和 Kernel 标注请求经过的职责。把每个实际函数映射到七模块，并标记哪些是插件贡献。层、模块、包不要求一一对应。

从可见入口开始追踪，而不是先按照理想目录搬文件。沿创建 Task、进入 Operator／Leader、派发、保存结果、修改 Role、资源清理各路径，定位调用函数、写入事务、外部副作用和回执保存位置。

对每个关键记录填一行：对象、当前写入入口、读取者、主键规则、更新方式、运行时依赖。对每项外部动作填一行：何时发起、何时确认、重启后如何知道处置、是否已有幂等机制。

特别区分 Role 的当前配置与 Session 的实际配置；Provider Session 与 Yui 自有进程；Task 状态与执行状态；临时目录与正式结果。已有机制优先保留语义，不因命名不同就重新实现。

## 3. 接口采用清单

责任地图应同时包含两条路径：查询如何从持久化事实进入 Context／Surface；原子操作如何进入本地事务或实际执行，再将结果写回。另标注确定 CLI 操作跳过 Intelligence Plane 的直达入口，避免实现成每个操作必须调用模型。

后续任务共同采用以下边界：Task 原子操作；Context read／delta；Role 当前配置及实际执行快照；AgentEndpoint；资源准备与产物引用；Capability descriptor／call；Host 句柄生命周期。

每个边界标注预期拥有者和首个消费方。最少要证明 T03 与 T04 可以通过接口交换执行目标和结果，而不互相修改私有表；T05 的资源可以被 Execution 使用但 Task 不需要知道 Git。

不在此任务冻结全部 provider 选项、所有能力名称或复杂通用 schema。只冻结后续并行工作确实会共享的部分。

## 4. 验证基线

在可丢弃 Home 中建立一组代表数据：Draft、Active Task、Role 配置、WorkItem、成功与失败 Turn、结果引用、待处理消息及一个未决操作。使用当前实现支持的途径构造，不伪造生产数据库。

正常路径覆盖 setup／配置查询、全局 Operator 入口、Task 查看和进入、现有 Codex／Claude 路径、结果读取及一项软件资源动作。无需默认使用付费模型；无法离线验证的项目明确标成需要受权真实测试。

保存可观察输出与必要身份关系，而不是快照全部非确定性日志。后续替换实现可比较输出含义和事实归属，内部文件路径不必相同。

## 5. 存储与正常使用

此任务不迁 schema，也不在当前 Home 停进程。需要读取用户配置时避免导出密钥，测试仅复制可公开的结构或使用 fixture。

正常使用承诺定义在 Task 完成状态：后续每个迁移 Task 合并时可发布且主路径可用，不承诺任意开发中间提交或任意存储升级零停机。

## 6. 完成条件

S39 要求明确同一 Store、同一 Controller 和实现选择边界；S44 要求写清当前受支持的存储升级入口、备份方式及不能假定的旧版本读取能力。

输出是一份实施证据材料，不是“所有目标架构已经实现”的声明。它应让 T01／T02 能准确选择复用点，让 T03／T04／T05 可以并行而不各自创造一套状态来源。

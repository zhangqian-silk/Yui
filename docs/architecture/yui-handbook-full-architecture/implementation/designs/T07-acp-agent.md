# T07 技术方案｜ACP 接入与第三 Agent 验证

硬依赖：T04。

任务定义：[交付范围与证据](../tasks/T07-acp-agent.md)。

## 1. 选择验证对象

选择实施时实际支持 ACP 的 CLI，记录版本、启动命令、协议版本及需要的认证。优先使用已经授权的本地配置，不为了证明抽象同时引入新付费账户和未知外部写入。

先验证 initialize、Session、prompt、事件、取消和权限的真实交互。规范、草案、CLI 实现可能不同，Endpoint 能力由实际证据决定，不由产品名字推断。

## 2. 协议与产品分工

ACP 适配实现公共消息、会话交互与结果映射。产品描述只负责发现 executable、版本、认证上下文和启动预设。载体使用已有 stdio 或其他被支持的连接方式。

如果第二个产品能复用该 ACP 代码，仅替换启动描述，应当无需改 Task、消息或结果归档。验证复用可以先用第二份产品 fixture；但第三 Agent 的主路径必须有真实 CLI 证据。

## 3. Endpoint 映射

按实际协议区分 submit 后即时接受和请求直到最终响应才结束的情况。正常长连接等待映射 pending，准确关联的最终结果可以作为完成及接受证据；连接丢失后的无法确认状态是 unknown。

协议 request ID、本地 attemptId 与原生 Session／Turn 身份分别保存。协议未提供原生 Turn ID 时保留 local-correlation，不生成一个 ID 冒称 native。

取消的回应也只表达实际证明的内容。未确认所有资源停止时不能以 cancel 请求成功代表物理静止。

## 4. 不支持能力

恢复、steer、用户原生并行输入、终端附件或工具用量可能未提供。Descriptor 如实表示，Agent选择其他方法；Controller 不增加产品名分支来模拟不存在的语义。

PTY 可作为人工接口，但不是结构化提交失败后的自动兜底。Codex native 路径保持独立，不强制为了统一 ACP 丢失已具备能力。

## 5. 实施切入

先用协议录制／fixture 覆盖边界，再注册真实产品描述。通过 T02 能力目录发现它，使用 T04 的普通执行请求创建 Turn，结果沿同一归档路径保存。

如果必须修改 Task Core 才能识别第三 Agent，检查泄漏的是产品发现、协议差异还是高层假设，并在负责层解决；不把新 Agent 写进 Task 的枚举。

## 6. 验收

S11、S12 覆盖身份与长等待；S24 覆盖 busy 与输入控制；S35 覆盖创建会话时选择实现。运行一条可控只读／本地资料任务，保存实际 CLI 版本、输入、终态、结果及权限处理证据。

模拟测试通过只说明 adapter 处理结构正确；真实测试未执行时明确标注，不能以产品 manifest 注册成功作为集成交付。

# T02 技术方案｜能力入口与内建实现接入

硬依赖：T01。

任务定义：[交付范围与证据](../tasks/T02-capability-entry.md)。

## 1. 入口和目录

建立一个 CapabilityRegistry，提供 search／describe／call。Descriptor 使用契约版本、输入输出 schema、效果类别、必要权限说明和 Provider 来源。核心模块内部继续允许 typed call，Registry 用于公共工具面与实现选择。

当前 CLI 或 Controller 命令处理器可以先成为 Provider。包装只适配参数、返回与身份，不复制 Task 数据，也不把所有函数重写成 Service。

## 2. 代码定位与首批能力

查找 Task 创建／编辑、Role 配置、WorkItem 派发、Runtime 检查、结果读取、消息和资源动作的真实入口。选择少量完整能力链，先让查询和一条本地修改可由新入口调用，再接外部执行请求。

每个包装器标出它调用的原事实入口及效果分类。对已经有外部请求记录的路径直接复用 operationRef，不能外面生成一个“成功”而里面仍在 unknown。

## 3. 可见性与歧义

宿主根据 Global、引用的 Project 和当前 Task 计算候选实现。Role 是否能使用某能力另检查授权，不把 scope 本身当 grant。

核心 namespace 保留给可信实现。局部同名贡献不能默默覆盖；显式 Provider 选择可用时使用它，否则唯一兼容者可直接选择，多于一个返回候选说明。配置默认选择也应有可追踪来源。

依赖仅支持明确的 required 名称／契约检查。缺依赖返回 unavailable。不要引入复杂优先级、自动下载和选择算法。

## 4. 调用处理

call 先描述并解析目标，再校验输入和当前权限，然后 acquire 选定句柄。查询直接调用；本地修改经事务；外部操作沿 T01 账本执行。输出 schema 校验失败保留操作记录和可能已发生的回执。

插件调用另一个能力仍传原可信上下文。查询能力不能通过嵌套写调用绕开效果和授权。该约束由公共调用入口执行，而不是要求 Agent 自觉遵守参数。

## 5. 正常使用路径

原公开入口可继续工作；新入口应调用同一业务 handler 或事务。逐步迁调用方时，用配置或装配选定一个 Provider，而不是两个 handler 同时接受一次请求。

如果实现选择切回内建路径，只影响新的、安全可重做或确认未发出的请求。未知外部效果不能触发自动 fallback。目录查询本身可以重建，不需保存另一份权威状态。

## 6. 验证

对同一 Task 编辑分别通过原入口和新入口验证结果；检查只有一条业务修改来源。注册两个同名测试能力验证歧义，显式选择后验证调用正确。

构造一个 Task-local 插件尝试声明核心管理名字和伪造 actor，验证拒绝。构造输出不合 schema 但外部服务已执行的插件，验证错误不抹掉回执。

S25、S30、S34、S39、S45 覆盖上述边界。完成后，T03／T04／T05 可分别接管其 Provider 实现，不必同时改整个调用链。

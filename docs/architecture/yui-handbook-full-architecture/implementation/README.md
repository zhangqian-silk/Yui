# 实施路线

## 1. 交付目标

实施从当前 Yui 可用能力出发，逐项建立本手册定义的边界。目标不是移动目录或增加抽象数量，而是每个任务都交付一个完整、可验证且保持产品可用的结果。

同一迁移 Task 可以由一个 Leader 负责，再按真正独立的责任划分 WorkItem。本文列出的实现步骤是参考路径，Leader可以根据当时源码调整顺序，但应满足目标接口和验收条件。

## 2. Task 依赖

```text
T00 实施基线
 └─ T01 基础宿主与操作事实
     └─ T02 能力入口
         ├─ T03 Task / Role / Context ── T06 Surface
         ├─ T04 AgentEndpoint ───────── T07 ACP
         └─ T05 Project / Resource

T03 + T04 + T05 ── T08 Draft Leader
T02 + T05 ──────── T09 Plugin SDK
T03 + T04 + T09 ── T10 原 Task 自扩展
T04 + T09 ──────── T11 热插拔
```

T10 的 Active Task 闭环不依赖 Draft；需要同时验证 Draft 自扩展时再加入 T08。不同任务可以并行规划，实现涉及共享接口时先明确接口负责人和最小契约，不让多个分支分别创造同一事实模型。

完整机器可读定义见 [task-index.json](task-index.json)。各 Task 卡片包含目标、依赖、责任边界和证据要求；对应技术方案描述接口、存储、实施路径和异常处理。

## 3. 保持正常使用

纯新增能力可以直接接入；能完整等价替换的实现可以一次切换；暂时不宜替换的实现允许保留两份代码。每次调用或 Session 只选择其中一份，不在动作未知时自动执行另一份。

允许并存的是实现，不是两套 Task、Role、Turn 或操作处置。使用一个 Controller 和一个权威 Store。Schema 更新走当前产品支持的显式升级契约，保留可验证备份，不假定任意旧 binary 能读新存储。

每个迁移 Task 合并后应完整可用；开发中的中间提交不要求全部可发布。旧路径删除不是每个 Task 的必要目标，也不要求预先拆成机械的引入／切换／删除三个任务。

## 4. 验收分层

契约测试在可丢弃环境中验证结构、权限入口、生命周期、重放和结果关联。产品路径验证确认真实 CLI／Runtime／资源能工作。不能使用 mock 输出声称真实 Agent 已通过。

对真实账户、付费额度、共享目录或外部写操作，先确认对应资源与授权边界。普通 Task 测试默认使用临时 Home、fixture 和受控资源，不接触正在使用的任务。

文档与 TypeScript 检查仅验证文档结构及类型关系。场景索引中的 `planned` 表示待实施验证，而不是已经运行成功。

## 5. 代码定位方式

实施时先按职责搜索当前源码：记录 Store、公开命令、Role 配置、实际启动和投递、结果归档、资源创建与清理。文件名只作为当时的定位结果，不写成跨版本必须存在的承诺。

开始改动前确认三件事：同一事实由谁写入；当前用户主路径走哪里；新入口如何共享既有事实。完成后记录实际修改位置及测试证据，供后续 Task 继续工作。

## 6. 里程碑

| 里程碑 | Task | 可用结果 |
|---|---|---|
| 基础边界可用 | T00–T02 | 内建能力使用同一受权入口与实例宿主 |
| 日常工作解耦 | T03–T06 | Task 事实、Runtime、资源和 Surface 各守职责 |
| 交互与扩展验证 | T07–T10 | 第三 Agent、Draft Leader、真实自扩展 |
| 实现可替换 | T11 | 按调用／Session 边界热插拔 |

这些里程碑是验收视角，不是额外运行状态。

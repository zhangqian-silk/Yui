# 实现取舍原则

## 1. 先判断是否需要框架机制

能够由 Leader 根据现有事实判断的事项，优先提供信息和操作。需要跨会话接手、需要保护资源或需要确认外部效果的事项，才进入持久化和机械检查。

不要把“有一个分支可以自动处理”直接等同于“必须建立自动恢复策略”。一个清楚的错误、结果引用和可调用工具往往已足够。

## 2. 少量概念具有明确责任

普通模块、插件包、数据库记录和运行实例不是一一对应关系。一个 Plugin 可以包含产品和协议代码；一个 Turn 可以保存 Assignment 快照；一份操作记录可以表达整个受控动作及部分回执。

只有独立复用、替换或生命周期确实需要时才拆分。不要为每个 parser、每个 Hook 或每个领域名增加一级 Registry。

## 3. 查询不产生业务事实

Context、目录、UI 状态和资源观察可以重建。读取不表示已经落实要求，也不表示消息已接受。运行观察带时间，不伪装成任务当前真相。

## 4. 更新不改写过去

Role 配置更新、插件更新和 Brief 编辑影响之后的判断与执行。历史输入、输出、Candidate 和回执保持来源清楚。是否继续使用某结果由 Agent 决定，而不是统一 revision 比较。

## 5. 错误范围尽量局部

一个面板不可用不阻止读取 Task；一个 Worker 失败不阻止另一项独立工作；一个插件缺失不删除它已产生的结果。只有当前动作确实涉及权限、错误对象或未知重复效果时，才拒绝该动作。

## 6. 安全承诺对应实际实现

提示不是权限，scope 不是隔离，类型不是身份认证，超时不是停止进程，取消请求不是取消完成，本地账本不是外部 exactly-once。

这些区别需要保留最少证据，不需要因此建设庞大的统一政策平台。采用明确、可验证且符合用户信任选择的执行边界。

## 7. 实施按交付结果收敛

每个 Task 以正常使用、接口行为和证据完成，不以删除多少代码、创建多少抽象或测试数量为目标。可以保留临时实现路径，但不保留两套可写业务真相。

真实未验证的能力明确说明。mock、文档和类型检查可以支撑开发，不能替代原生协议或实际资源验收。

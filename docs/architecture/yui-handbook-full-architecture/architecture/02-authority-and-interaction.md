# 职责、交互与任务生命周期

**层次位置：Intelligence Plane，通过 Experience Plane 与用户交互，通过 Capability Plane 使用 Yui Tools。** 实际模型由 Execution Plane 承载。这里定义负责人和决策权限，不定义另一个运行时或工作流引擎。

## 1. 用户与 Operator

用户拥有最终权威。Operator 是自然语言操作代理，可以在用户权限范围内管理 Project、Task、Role、Agent、插件和执行。它不是只能创建任务的低权限分发器，也不是必须替所有 Leader 持续排程的上层主管。

Operator 根据请求的耦合关系、独立结果和用户预期划分 Task。与当前 Task 相关的细节可以直接交给其 Leader；跨多个 Task 的安排由用户或 Operator 处理。跨 Task 建议使用普通消息和知识，不需要专门的任务提案状态机。

```text
用户 ↔ Operator：全局安排、配置、任务边界
用户 ↔ Leader：目标细节、方案、执行与结果
Operator ↔ Leader：需求变动、跨任务信息、必要干预
Leader ↔ Worker / Reviewer：具体责任与反馈
```

## 2. Leader 的完整责任

每个 Task 有一个逻辑 Leader。Leader 对任务结果负责，可以直接完成工作，也可以创建 WorkItem、分配角色、启动多个执行、请求 Review 或调用资源动作。

唯一负责人是协调规则，不剥夺用户和 Operator 的直接操作权。用户或 Operator 进行明确干预时，使用相同原子入口并留下来源。Leader 读取变化后调整方案。框架不再额外运行一个隐藏 Agent 来决定谁应当重做。

同一个逻辑 Leader 可以更换模型、Agent 或 Session。逻辑身份与实际执行者分开，避免换会话时重建整个 Task。对一个 Role 的执行请求通常串行接收；多个 Role 的工作可以并行。

## 3. 从 Draft 开始协作

Task 创建后即可建立 Leader Role。首次进入对话时按需启动或恢复 Session，不要求每个 Draft 常驻进程。

Draft 中的 Leader 可以读取项目知识、对齐要求、修改 Brief、记录重要决定、设计 WorkItem、研究问题和运行授权的临时实验。这里的结果属于规划材料，允许保存为供后续引用的 Artifact；不会仅因为创建了文件而被视为正式交付。

正式执行请求使用 Task 的 delivery authority。Draft 本身没有这类权限。权限边界由 Yui 工具和实际环境共同实现；若用户选择宽权限本地 Agent，文档中的角色约定不能替代真实文件系统隔离。

## 4. Activation 的含义

Activation 表示用户或受权 Agent 允许任务开始正式交付。它记录当时的任务说明引用和执行配置，准备必要资源，并使 Task 进入 active。它不把方案变成不可变约束，也不使之后的每次需求修改都必须重新激活。

环境可以为空。仅进行资料整理的 Task 不需要为了符合框架模型创建 Git worktree。需要准备外部环境时，先准备，再在一次状态更新中采用；准备失败仍可继续讨论 Draft。

激活时不会把正在运行的 planning Turn 即时升权。由当前 planning Turn 发起的激活请求，可以记录在现有操作记录中并立即返回请求引用，在该 Turn 结束后采用；不让工具调用等待自身结束。

原生 Session 的环境和权限可安全续用时继续同一个会话。否则创建新 Session，由持久化 Context 承接。会话连续性是体验，不是高于权限和事实的硬要求。

## 5. 对话中的信息管理

用户直接向 Leader 提供的信息，若影响之后的工作，由 Leader 写入当前 Brief、Decision 或 WorkItem。临时提问、试探性方案和一般交流可以留在原生对话中。

Yui 不增加自动语义提取 Agent。也不要求每次回复前都持久化一段摘要。Leader 在需要依赖信息跨会话存在时保存它，并通过简短回复说明重要选择已记录。

若原生输入能被可靠观察，可以保留可见输入及来源；不能观察时，不推测、不伪造用户消息。持久化之前发生的会话丢失，可能需要查看原生历史或再次询问用户。

## 6. 工作完成与结果判断

WorkItem 是独立责任；Candidate 是一版结果；Review 是针对结果的意见。它们帮助 Leader 管理交付，不规定所有 Task 必须使用同一套对象链。

简单的 direct Task 可以由 Leader 提交完成说明和必要产物引用。需要独立验收的 WorkItem 则通过 Candidate 明确选择被接受的结果。框架检查引用和权限，不从 Reviewer 文本或测试退出码决定接受。

任务状态变化不等于物理取消所有外部活动。Leader 完成或取消任务时，应明确仍在运行的执行怎样处理。迟到结果仍按原 Turn 保存，不自动重新打开任务或启动新的工作。

## 7. 配置切换与干预

Role 保存当前希望使用的 Agent、指令、Skills、模型、权限选择等。更换 Role 配置通常作用于下一次执行。已有 WorkItem、结果和消息继续存在。

若 Operator 更换 Leader 的实际执行承载，需要让旧承载不再提交新的管理动作；旧执行已经产生的结果仍然可记录。撤销管理入口不代表物理进程已经停止，对相同资源的冲突执行应按实际环境处理。

这是授权与资源边界，不是要求创建复杂的领导者选举系统。单用户部署采用现有 Role／Session 绑定校验即可。

## 8. 故障责任

工具参数错误首先返回调用者。Worker 或 Reviewer 的执行无法继续时，事实进入 Task 并通知 Leader。Leader 本身无法继续或主动求助时，通过现有消息路径通知 Operator。

Operator 的问题由用户自行处理。系统不创建备用 Operator、恢复 Task、专用救援运行时或 Operator 自动修复循环。普通配置、检查和启停入口仍然是用户可用的工具。

通知说明事实，不附带框架预定的业务恢复计划。有限连接维护可以保证已提出的动作被准确观察，但不因此自动更换 Agent、重做工作或重新提交效果未知的输入。

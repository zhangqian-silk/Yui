# 能力、插件与资源

**层次位置：Capability Plane、资源执行能力和横向 Plugin Fabric。** Agent 面向公开能力工作；具体工具和连接在执行层实现；Kernel 始终提供共同权限和实例宿主。

## 1. Capability 是 Agent 的操作模型

Agent 使用清楚命名的能力完成工作，例如读取任务、委派 WorkItem、查看结果、读取资源或激活插件。Capability 描述应足以让调用者知道输入、输出、作用对象和可能的副作用。

```text
capability.search / describe / call
plugin.create / validate / activate / disable
```

名称是工具面，内部可以使用类型明确的函数或 Service。系统不要求所有内建方法都成为字符串调用，也不要求每项能力都有独立服务实例。

能力目录来源于当前配置和已加载实现，是可重建的读模型。Task 事实不依赖“某个插件现在一定在线”。调用时发现实现不可用，返回该事实，Leader 可以重新启用、换方法或补充实现。

## 2. 最小能力描述

一项能力至少描述名称、契约版本、输入输出约定、效果类别及实现身份。效果可简单区分查询、本地修改和外部操作。需要权限的资源由具体动作明确要求，不建立万能资源政策语言。

宿主从可信入口得到调用者身份；调用参数里的 taskId 只是目标，不能用 JSON 字段冒充 Operator。Task-local 插件不能覆盖核心管理命名空间。

如果可见范围里有多个同名实现，可以使用显式配置或由 Agent 选择。没有明确选择且无法唯一解析时返回歧义，不按加载顺序静默覆盖。一次调用选定一个实现，不在执行途中更换。

## 3. 插件与数据型扩展

```text
具体插件 / Role 模板 / Skill 数据
                    |
             注册或应用贡献
                    |
     +--------------+------------------+
     |              |                  |
  命令与视图     行为与配置         具名原子能力
 Experience   Intelligence         Capability
                                        |
                                  实际工具 / Endpoint
                                     Execution
                                        |
                    Kernel 唯一宿主管理实例、权限与生命周期
```

插件贡献可以跨层，但不会获得跨层改写事实的权限。每一项写操作仍由所属模块和共同授权入口处理。

可执行插件用于实现工具、Runtime 适配、资源操作或需要代码的贡献。Role 模板、Skill 和简单工具映射优先作为数据，由受信任解释器处理，不必为了“插件化”都变成可执行代码。

插件 manifest 保持小：id、version、apiVersion、entrypoint、provides、requires、permissions 和 reloadMode。只声明真实需要的依赖，不引入复杂优先级求解或多级 Bundle 工作流。

Scope 只有 Global、Project、Task。它决定配置归属和可见范围，不自动授予资源权限，也不是代码隔离机制。多个 Project 可以提供不同能力，同一个 Task 可以同时使用它们，不需要领域标签。

## 4. Project 与 Resource

Project 是长期工作背景：名称、说明、知识、资源引用和默认能力配置。Project 不等于 Git 仓库，也不承担任务排程。

Resource 的通用部分只有稳定身份、类型和必要元数据。具体能力由插件提供，例如 `git.diff`、`document.read`、`browser.search`。Core 不要求所有对象都实现相同的 read/write/execute/publish 接口。

Task 引用 Project 不等于获得 Project 的全部凭据。实际访问还需要相应授权。资源插件负责解释版本、外部句柄和操作回执，Yui 负责保留这些结果与所属任务的关系。

## 5. 环境与产物

Environment 描述一次执行实际使用的目录、挂载、网络、凭据和限制。它可以是普通本地目录、受限临时环境、已有容器或远程服务，也可以对无文件需求的任务为空。

环境不必成为 Task 的强制一等工作区。只有存在资源使用和清理责任时才记录环境归属。角色不因为拥有一段提示就获得文件系统写权限。

Artifact 是可引用的工作成果。内容文件可以保存摘要或独立副本；外部成果可以引用明确版本；已经执行的动作可以引用回执。Core 保留基本信息和引用，不理解报告格式或 Git 结构。

## 6. Agent 自扩展

Leader 在原任务中发现能力不足时，先判断是否可以用已有工具直接完成。一次性脚本已经足够时，不要求建立插件。需要重复调用、复用或加入能力目录时才实现插件。

```text
查找能力 → 选择复用／组合／编写
       → 编写实现与输入输出说明
       → 验证
       → Task-local 激活
       → 经稳定调用入口使用
       → 保存原任务的实际结果
```

编写插件不是另一个强制 Task 类型。Leader 可以自己做，也可以委派给 Worker；软件开发能力只是完成这项工作的工具。系统不自动把每次 validation failure 转成修复 WorkItem。

## 7. 验证与执行信任

验证涵盖可解析的 manifest、类型和契约、加载卸载、声明能力是否完整，以及所选执行环境下的测试。报告绑定实际测试的代码产物，源文件更改后需要重新验证对应产物。

构建和测试也会执行代码，应使用同样清楚的授权边界。Agent 生成的可执行代码不默认导入控制进程。优先使用已有的受限环境和受权工具入口；用户明确选择 trusted-local 时，说明它依赖对代码的信任，不声称仅靠 manifest 提供隔离。

没有合适隔离时，可以先使用声明式能力或已有受权工具完成任务。缺环境是能力事实，不是必须构建一个全新沙箱平台的理由；扩大权限或信任范围由用户／Operator 的授权约定决定。

## 8. 能力增加与权限增加分离

Task-local 插件可在已有授权范围内自动激活，不必每次再让用户确认同一权限。新增凭据、外部写入权限、全局替换或更高信任级别，则应提出明确请求。

插件经由 Yui 再调用其他能力时，仍使用原调用者的权限，不能把一个查询能力包装成任意写入能力。发生部分效果时，保留已经得到的回执；输出格式错误也不会使真实外部效果消失。

## 9. 同一会话使用新能力

Agent 启动时已有稳定的 Yui CLI 或 describe/call 桥。插件激活后，下一次目录查询可以发现新能力，后续调用直接使用。这个桥不属于 Agent 必须先自己安装的插件。

因此自扩展不依赖原生 Agent 支持即时修改工具 schema。Skill 提醒 Agent 在缺能力时查询目录，而不是要求每次插件更新都重启所有会话。

## 10. 能力沉淀

Task-local 实现可以在工作结束后作为源文件和验证材料保存。需要跨任务复用时，Operator 可以将其配置到 Project 或 Global。这是一次普通受权配置操作，不需要 promotion 状态机。

扩大可见范围不会自动扩大资源授权。其他 Task 仍按自己的权限调用。历史 Candidate 只引用实际结果，不决定插件代码应保留多久。

具体接口见[Plugin 与 Capability 模块](../modules/06-plugin-capability.md)；环境和产物职责见[Project 与 Resource 模块](../modules/05-project-resource.md)。
